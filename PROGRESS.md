# Progress: seatbelt build

## Status: v2 pivot — enforcement stripped, seatbelt is re-injection only

**Product decision (2026-09-24)**: after two rounds of structural detection work produced non-monotonic, ecosystem-dependent blind recall (12% -> 60% -> 40%, see the archived history below), the enforcement side of seatbelt is cut. seatbelt no longer tries to detect or classify dangerous commands. Its only remaining job: keep the user's own CLAUDE.md/AGENTS.md rules alive in context across compaction, resume, and context depth. Full reasoning and the complete numbers table: [docs/ARCHITECTURE_DECISION.md](docs/ARCHITECTURE_DECISION.md).

All removed code (PreToolUse hook, tokenizer, risky-command list, structural detector, reversibility axis, all eval/dataset tooling) is preserved on branch `archive/enforcement`, branched from commit `4e4f810`. Nothing was deleted from history.

### v2 Phase 2: re-injection content decision

### v2 Phase 3: depth-triggered re-injection (`UserPromptSubmit`)

New hook `scripts/depth-check.js`, registered on `UserPromptSubmit` in `hooks/hooks.json`, plus `scripts/session-end.js` (state cleanup) registered on `SessionEnd`. Addresses the long-known, previously-logged-but-unsolved limitation (docs/DESIGN.md #1, docs/EVIDENCE.md): a session that never compacts still loses rule adherence purely from context depth, and `SessionStart`'s `compact`/`resume`-only trigger never covers it.

New library modules:
- `scripts/lib/estimate-transcript-tokens.js`: ~4 chars/token, exact read under a 2MB cutoff, byte-size estimate above it (bounds the added per-turn cost on very long transcripts).
- `scripts/lib/depth-decision.js`: pure `shouldFire()` — fires at `firstFire` tokens (first time), then every `interval` tokens past the last actual fire point (not a fixed multiple of `firstFire`), gated by a `minTurnsBetween` floor that blocks any fire regardless of token math.
- `scripts/lib/depth-state.js`: per-`session_id` state file in the OS temp dir (last-fired tokens, turns since fire), sanitized against path-traversal characters in the id, best-effort read/write (corrupted or missing state degrades to "never fired" defaults, never a crash).

Threshold defaults (`firstFire: 100000, interval: 50000, minTurnsBetween: 10`) and their justification (measured degradation zone starts 50-100K, stable region to ~40% of Claude Code's ~200K window, an existing community hook's 90K precedent) are recorded in docs/DESIGN.md's new "v2: depth-triggered re-injection" section, along with the tested injection phrasing and the `--continue`/`--resume` replay interaction (stale depth-injections in a replayed transcript are a non-issue because `SessionStart`'s `resume` trigger already re-injects fresh rules at the moment of resume).

Injection phrasing changed to match session-start.js's plain "Project rules from CLAUDE.md/AGENTS.md:" framing (not a directive envelope), per this phase's explicit requirement that hook-injected text not read as an out-of-band system command.

New tests: `tests/depth-decision.test.js` (12), `tests/estimate-transcript-tokens.test.js` (5), `tests/depth-state.test.js` (9), `tests/depth-check.test.js` (6), `tests/session-end.test.js` (3) — covering threshold edges, interval-relative-to-last-fire behavior, the turn floor, config parsing integration, path-traversal sanitization, corrupted/missing state, and fail-open on an unreadable transcript path. Manually verified end-to-end via direct stdin invocation: fires once at the threshold, does not re-fire on a second identical call, cleans up correctly via session-end.js.

Gate met: 86/86 tests passing (up from 51).

### v2 Phase 4: adherence measurement (the eval that actually matters)

Built `evals/adherence/` (`rules.js` — 3 mechanically-checkable rules; `padding-prompts.js` — 20 topically-unrelated realistic work prompts; `run-adherence.js` — the harness). Ran it for real against the live `claude` CLI: headless `-p`/`--resume` sessions padded to 25k/50k/100k/150k/200k token checkpoints, probed per rule at each checkpoint, across both `seatbelt-enabled` and `seatbelt-disabled` conditions (30 rows total, `evals/results/adherence-raw.jsonl`).

**Two real, previously-undetected bugs were found by running this for real, not by unit testing:**
1. **`scripts/session-start.js` emitted `additionalContext` at the top level of its output JSON instead of nested under `hookSpecificOutput.additionalContext`** — the actual Claude Code hook contract. Confirmed via a live `--debug hooks --debug-file` trace: `Hook JSON output had unrecognized keys (ignored): additionalContext`. This means `SessionStart` re-injection — the original v1 feature this whole project started from — has been a silent no-op in production the entire time, undetected because no test ever checked the real stdout JSON shape (only `buildContext()`'s return string). Fixed, and reconfirmed via the same live trace showing Claude Code accepting it (`provided additionalContext (111 chars)`). New end-to-end schema tests added to `tests/session-start.test.js` and `tests/depth-check.test.js` that spawn the real script and assert against this exact failure mode, so it can't regress silently again. Also fixed a bug in the harness itself found while running it: `runPaddingUntil` re-derived "has this session started" from a locally-scoped variable reset every call, wrongly re-issuing `--session-id` on an already-started session past the first checkpoint (Claude Code correctly rejected it: `Session ID ... is already in use`).
2. **`SessionEnd` fires after every individual headless `-p` invocation, not once per logical multi-turn conversation** — confirmed via the same live debug trace. Since `session-end.js` deletes `depth-check.js`'s temp-dir state on `SessionEnd`, cross-turn state (`lastFiredTokens`, `turnsSinceLastFire`) was wiped after every padding turn in this harness.

**Result: a null result, honestly reported, not manufactured into a number.** `british-spelling` and `no-delve` held at 100% adherence at every checkpoint out to 200,000 tokens in BOTH conditions (seatbelt made no measurable difference because nothing decayed regardless). `summary-prefix` failed at every single checkpoint in BOTH conditions, including the very first (25,000 tokens/turn 1) — suggesting it was never followed even fresh, not that it decayed with depth, which points at the rule/probe design rather than a re-injection failure. The `session-start.js` bug fix landed mid-run (after the disabled condition, during the enabled condition), so this specific run's `seatbelt-enabled` data is a mixed pre-fix/post-fix sample and cannot be read as a clean test of the fixed code. Full analysis, all three causes, and the honest bottom line: `evals/adherence/RESULTS.md`.

Per this phase's own fallback instruction: this is not "headless mode can't support this" (it worked mechanically end to end) — it's a first real run surfacing infrastructure bugs before the number can be trusted, reported as this phase's real output rather than papered over. A clean re-run post-fix, ideally against a workflow that triggers genuine `/compact` rather than just `--resume`-accumulated depth, would be needed for a confident adherence-curve number; not performed in this phase given cost/time already spent (~35-40 min wall time, several dollars in API usage for the one run).

Gate met (per the phase's own OR condition): real data collected, all 30 rows honest and unmodified; the run's limitations are documented plainly rather than hidden. 90/90 unit tests passing (up from 86, new end-to-end schema tests).

**Most recent, most important finding**: round 2 (a reversibility/consequence axis + verb-family expansion + morphology/non-POSIX-syntax parsing, built specifically to close round 1's generalization gap) improved round 1's burned holdout2 from 60.0% to 68.0% dangerous recall — but a FRESH, independently-built third holdout (embedded/firmware tools, HPC schedulers, network-device CLIs, ERP/mainframe tooling — ecosystems neither round had touched) scored only 40.0%, LOWER than round 1's own blind result. ### Structural rewrite: Phase 1 (build + tests)

Built 6 independently-testable signals (A-F), each with its own predicate function and unit tests (81 tests total across all 6 signals plus combined-evaluation cases, well over the required minimum of 8 each). Every signal maps to `ask` only, never `deny` — hard deny remains reserved for a user's own guard-tagged rule, protecting the deny-precision number.

3 real bugs found and fixed while building against the full test suite (not fixed by adding tool names — fixed by narrowing the structural rule itself, consistent with the plan's hard rule):
1. **Signal A too loose**: matched `--help`/`-h` as a "target" (false-positived on `git reset --help`, `rm --help`), and included `uninstall`/`remove`/`rm`/`kill` in the destructive-verb list, wrongly flagging routine package uninstalls (`npm uninstall lodash`, `pip uninstall x -y`) and any `rm <file>` with no recursive/force flag. Fixed by requiring a real target (excluding `--help`/`-h`/`--version`/`--dry-run`) and removing `uninstall`/`remove`/`rm`/`kill` from the verb list (kill is separately covered by signal B's `-9`/SIGKILL check; bare filesystem `rm` without `-r`/`-f` is genuinely low-risk and reversible via git).
2. **Signal C's prod-target check fired standalone**: `export NODE_ENV=production` (a harmless env var assignment) was flagged just for containing the word "production," with no action verb at all. Fixed by requiring an action-indicator word (stop/restart/delete/deploy/etc.) alongside the prod/production/live mention.
3. **Signal B's --recursive+rm check caught `git rm -r --cached x`**: a common, safe git operation (untracking files without touching them on disk) inherently contains both "-r" and "rm." Fixed with a narrow, explicit exception for `git rm ... --cached`.
4. **Signal F's irreducible-list check was free-text search, not head-command-aware**: matched "wipefs" appearing inside a URL (`curl .../wipefs-notes.md`) — the exact bug class the tokenizer exists to prevent, reintroduced by not using `headCommand`. Fixed to check the head command specifically via the already-defined but previously-unused `IRREDUCIBLE_HEADS` set.
5. **Signal C's cloud-URI check fired on read-only operations**: `aws s3 ls s3://prod-bucket/...` (listing, not deleting) was flagged just for containing an s3:// URI. Fixed with an explicit-read-only-verb exclusion (`ls`/`cat`/`get`/`describe`/etc.).

Gate met: 177/177 unit tests pass (up from 96 before this rewrite).

## Round 2: reversibility axis, verb families, morphology/non-POSIX parsing

### Round 2, Phase 1 (reversibility/consequence axis)

Built `scripts/lib/assess-reversibility.js`: 4 independent axes (scope — project-local/system/whole-device; re-derivability — node_modules/build/dist/etc. vs. unique state; reach — local/remote/shared-account-CLI; confirmability — does the command suppress a confirmation prompt) combined into a single `highConsequence` gate. This is what let "uninstall"/"remove"/"rm"/"kill" back into signal A's verb vocabulary (round 1 had excluded them entirely to avoid a false positive) — "npm uninstall lodash" now correctly falls through as low-consequence (project-local, re-derivable, no force flag) while "brew uninstall --force x" correctly fires (force flag suppresses confirmation regardless of target).

46 unit tests, including 22 same-verb contrast pairs (more than double the required 20) contrasting identical verbs with opposite real-world consequence. 6 real bugs found and fixed during test-writing, each corrected with a narrower, more precise structural rule rather than a broader one: (1) bundled `-f` flags (git's `-fd`) weren't recognized as suppressing confirmation; (2) `rm -rf`'s own `-f` was wrongly counted as confirmation-suppression (rm has no default confirmation to suppress) — excluded via a specific `-rf`/`-fr`-on-rm carve-out; (3) a bare `dropdb production` had no positive high-consequence signal at all — added "prod/production/live" as a reach factor (a resource explicitly labeled shared/production is high-consequence regardless of physical location); (4) cloud-CLI head commands (terraform, kubectl, etc.) were flagged as "shared-account" unconditionally, even for read-only/local subcommands like `terraform state rm` — added a local-subcommand and explicit-read-only-verb exclusion, mirroring structural-danger.js's existing discipline; (5) a generic "any absolute path outside the project" scope was tried for `shred -u /home/user/x` and reverted after it produced a false positive on `npm run build -- --outDir /tmp/output` (a benign flag value coincidentally shaped like a path) — replaced with the narrower, safer fix of adding `/home` to the explicit system-path list; (6) any `scheme://` URI is now recognized generically (was previously an enumerated list of `s3/gs/oci/azure/https/ssh`, missing `sftp` and others).

Gate met: 46/46 same-verb contrast and unit tests pass.

### Round 2, Phase 2 (verb families, morphology, non-POSIX syntax)

**2A — verb families**: rebuilt `DESTRUCTIVE_VERBS` as 7 named semantic families (removal, termination, reduction, revocation, reset, separation, destruction) with real-world synonyms per family, rather than a flat list grown by adding whichever words a failing test needed. "uninstall" lives in the removal family and is gated by the reversibility axis, not excluded outright.

**2B — morphology**: built `splitMorphology()` (camelCase/PascalCase/kebab-case/snake_case tokenizing), `matchesFusedVerbPrefix()` (lowercase fused compounds like "deletelocalsnapshots"), and `matchesPowerShellVerbNoun()` (PowerShell's Verb-Noun cmdlet convention, e.g. `Remove-Item` -> verb "remove"). Wired into signal A as a fallback when the plain-word regex finds nothing, scanning every word in the command (not just the head command) for a morphology or fused-prefix match, after an earlier version that only checked the head command missed verbs embedded in arguments (`diskutil eraseDisk`).

**2C — non-POSIX flag syntax**: added colon-value flag detection (`force:true`, `skip_clean:false` — fastlane/Ruby-CLI convention) to the confirmation-suppression check, generically on the key name and boolean-looking value, not on any specific tool.

Found and fixed one more real false positive during this phase's testing: `pip uninstall pinecone-client -y` (a real row from the training dataset) was wrongly flagged once "uninstall" re-entered the vocabulary, because a bare package identifier with no path at all scored `scope: unknown` (not positively low-consequence) rather than being recognized as package-management shape. Fixed with a narrow, verb-scoped exception: "uninstall" specifically, with a bare `[\w.@-]+`-shaped target and NO `--force`/`-f` flag, is treated as low-consequence — scoped tightly enough that `brew uninstall --force x` (which does carry `--force`) still fires correctly, and the exception does not touch `delete`/`drop`/`destroy` detection on bare identifiers elsewhere (`dropdb production`, `redis-cli FLUSHALL` are unaffected).

68 additional unit tests (114 total in structural-danger.test.js). Gate met: full suite (256 tests) passes; main-dataset eval returns to exactly the pre-round-2 baseline (96.9% overall, 0.0% safe FPR, 100.0% deny precision) — the vocabulary/morphology/non-POSIX expansion added zero net regression on the training-adjacent set while fixing real cases on both burned holdout sets (holdout1 dangerous recall 72.0%->68.0%, roughly flat within noise; holdout2 dangerous recall 60.0%->68.0%, near-miss held at 100.0%).

## Prior status: VERDICT REVISED: the 99.1% dangerous-recall figure does not generalize

**Most recent, most important finding**: a held-out generalization check (25 dangerous rows + 15 near-miss rows, using tools/syntax never present in the training-adjacent dataset — different package managers, cloud providers, databases, system utilities) found dangerous-command recall collapses from 99.1% to **12.0%** on genuinely novel tools. The near-miss/precision mechanism generalized much better (86.7% vs 91.1%). Full detail: [evals/results/HOLDOUT_REPORT.md](evals/results/HOLDOUT_REPORT.md), [evals/results/HOLDOUT_OVERLAP.md](evals/results/HOLDOUT_OVERLAP.md). This is not a new bug — it is the expected, now-measured consequence of Phase 3 building its risky-command list by mapping every new pattern to a specific known failure (as that phase was explicitly instructed to do), which produces a list that recognizes specific tools it has seen, not the general categories it is named after. Both VERDICT-2.md and README.md have been amended (not overwritten — both old and new numbers are shown, labeled) to reflect this. Revised bottom line: seatbelt is a reliable guard for the specific tools already enumerated in `scripts/risky-commands.js`, and offers close to no protection for the same categories of damage via a different, unlisted tool.

## Real bugs found during the eval rebuild (verified directly, not just observed as eval failures)

1. **Newline-sensitivity in the built-in "git push" regex.** `\bgit\b(?:(?!--dry-run).)*?\bpush\b(?!.*--dry-run)` uses `.` without the `s`/dotAll flag, so a command with a literal embedded newline between "git" and "push" is not matched, even though the same text on one line is. Verified directly and isolated to this exact cause.
2. **Non-breaking-space (U+00A0) evasion.** A non-breaking space in place of a normal space between "git" and "push" breaks the implicit whitespace matching. Verified directly.
3. **POSIX-style path handling silently breaks rule discovery on Windows.** `findAndParseRules()`/`loadConfiguredRisky()` use `path.join()`, which does not treat a POSIX-style absolute path (e.g. `/d/skill/project`) as absolute on Windows — it silently produces a nonexistent path, so CLAUDE.md/AGENTS.md/rule-guard.config.json are never found, and the tool falls back to "no rules" with no error surfaced. Confirmed with a clean, unambiguous test: the identical directory works via its Windows-style path and fails via its POSIX-style path. Severity in real-world Claude-Code-on-Windows-with-Git-Bash usage is flagged as plausible but NOT directly confirmed (would need to capture real hook input JSON from a live session on such a setup) — logged as a priority item to verify, not silently patched.
4. **Near-miss precision problem is structural, not a tuning issue.** Confirmed via Phase D: the false-positive rate on the near-miss bucket (commands that look risky but are actually `echo`, `grep`, comments, etc.) stays between 32% and 52% across all three risky-command-list strictness configurations. This proves the problem is in the matching logic itself (no awareness of command-position vs. string-argument context), not in which commands happen to be on the list.

None of these were fixed in this pass — per the eval task's explicit scope, this is a measurement and reporting exercise, and fixing the underlying code is separate, prioritized future work per VERDICT.md's recommendation.
